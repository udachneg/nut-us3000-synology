# 0026: диагностика отказа автозапуска

Локальный диагностический кандидат, не исправление подтверждённой причины и
не финальный релиз. Сам по себе не разрешает установку или новый тест на NAS.

## Что известно

В сохранённых наблюдениях 0025 два ранних запуска завершились общим rc=1;
поздний ручной запуск успешен. Во втором отказе сервер и USB-драйвер уже
запустились. Внешний таймаут пакетной службы равен одному часу, поэтому
восьмисекундный отказ нельзя объяснять истечением именно этого таймаута.

Локальная модель показала достижимую ветвь: два неуспешных наблюдения CORE
по 1600 мс исчерпывают трёхсекундное окно, после чего пакет сам останавливает
пару, не переходя к чтению данных UPS. Это объяснение **возможно, но не доказано
для NAS**. Одно долгое успешное наблюдение CORE не приводит к этому отказу.

## Что изменено

Только сообщения `NUT_START_DIAG` в stderr существующего процесса запуска:

- `layer=hook`: проверка окружения/конфигурации, RAM-start, публикация состояния,
  запуск контроллера; `operation_rc` — код операции, `rc` — итог hook.
- `layer=bridge`: bootstrap, locks, аутентификация payload, отдельные фазы
  prepare/ensure/audit/start/recovery; начало и результат фазы, итог dispatch.
- `layer=runtime`: preflight, USB probe, systemd start, CORE wait, data wait,
  unwind. Ошибки имеют фиксированные `reason` и `op`, транспортный статус,
  код дочерней команды и монотонное время от начала runtime START.

`elapsed_ms` bridge отсчитывается от начала bridge dispatch; у runtime собственная
точка отсчёта. Это не время одной команды. `-1` означает, что поле не применимо
или часы недоступны. Коды transport: 0=OK, 1=TIMEOUT, 2=LIMIT, 3=SIGNAL, 4=SETUP.
`child` действителен только при transport=0. stdout по-прежнему содержит только
прежний протокол `RAM_STATE=...`; никаких новых файлов, служб или наблюдателей.

Диагностика runtime включается только в фазе START; штатные опросы CORE/HEALTH
не засоряют журнал. Внутри ограниченных циклов могут повторяться записи об
ошибках; произвольные ответы команд, конфигурация, ключи и пароли не выводятся.

## Как различить причины

| Последовательность сообщений | Что она устанавливает |
| --- | --- |
| core_wait → exec_exit, op=core_inventory → core_deadline → unwind | Исчерпано прежнее окно после неуспешной инвентаризации; причина внутри скрипта ещё требует отдельного разбора |
| exec_transport, op=show_server или query_local | Не получен штатный ответ; transport различает timeout/limit/signal/setup |
| exec_exit, op=show_server, child=1 | systemctl завершился rc1; эта строгая проверка по-прежнему не принимает его как успех |
| unit_missing_field / unit_identity_control / unit_running_state | Отказ конкретной структурной проверки unit snapshot |
| data_identity / data_syntax / data_missing_field | Отказ проверки ответа upsc, а не ожидание CORE |
| data_deadline | Истекло отдельное прежнее окно готовности данных |
| hook stage=controller_start, rc=1 | Отказ произошёл после принятого результата RAM-start |
| unwind_failed | Само завершение неудачного старта не подтвердило безопасную остановку |

Смотреть первую неуспешную операцию и последовательность до unwind, а не
только последнюю строку complete. Например `inventory_mismatch` после
`exec_exit` — общий отказ инвентаризации, а не доказательство неправильного PID.
Результат bridge complete=1 после start result=0 указывает на сбой последующей
фиксации состояния/вывода; это не отказ запуска дочерних процессов.

## Что не изменено и не проверено заново

- CORE: 3000 мс; данные: 20000 мс; паузы и deadline команд — прежние.
- Условия отказа/UNAVAILABLE, проверки прав/identity, unwind, stop/uninstall,
  RAM units, USB-драйвер, восстановление после safe mode — прежние.
- Девять новых тестовых методов проверяют именно новые сообщения и сохранение
  кодов/протокола на моделях и в изолированном Linux-контейнере.
- Старые NAS/VM/USB/safe-mode/reboot тесты не повторяются. Холодный запуск
  диагностической сборки на NAS и сохранение stderr штатным DSM не проверены.

После отдельного разрешения сначала следует проверить получение диагностических
строк при обычном разрешённом запуске. До любого прерывания работы необходимо
проверить путь сохранения журнала. Окончательную причину исторических отказов
нельзя установить задним числом по информации, которую 0025 не записывала.
